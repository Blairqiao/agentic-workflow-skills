# Fast track

Apply [workflow core](../_workflow/core.md), including supplied-context reuse, and load the active adapter only. Follow this linear sequence without loading the full discovery/design/planning chain. Linked procedures are references; load details only when the current operation needs them.

1. **Fit.** Use fast-track for one bounded linear task with settled expected behavior. A follow-up defect is a mismatch with approved behavior; new behavior is new scope even with few changed files. No implementation subagents are allowed. Read-only exploration is permitted; load [discovery](../_workflow/discovery.md#code-exploration-and-delegation) for broad or unfamiliar investigation. Read applicable repository guidance, relevant tests/configuration, and `CONTEXT.md` when present. If diagnosis needs a product decision, new dependency, migration, security or architecture change, material risk, or multi-task coordination, stop dependent work and return to planning, recommending [full-track](../full-track/SKILL.md). Continue independent authorized work; a revised ready plan needs a new execution instruction.
2. **Authorize.** Before creating a record, perform step 3's starting-state checks. Standalone fixes run in a single chat with one [lean record](../_workflow/templates/fast-track.md) at `<main-repo>/.agent-docs/fast-track/<feature>.md`. For follow-ups, reuse the candidate checkout and exact parent plan, appending to the parent's proof when available. Before each standalone fix and every follow-up repair, present the mini-spec inline with scope, affected files, strategy, acceptance criteria, and verification; pause for explicit approval before editing code or tests. Parent behavior approval does not substitute for repair approval. Put the direct authoritative record link at the very bottom of the gate response. Diagnosis and independent read-only work may continue while waiting. Record approval and keep this record current on retries; do not duplicate the parent plan or create a taskboard for one fix.
3. **Starting state.** Before writing workflow records, identify the main repository with `git worktree list --porcelain`. Ensure `.worktrees/*`, `.worktrees`, `.agent-docs/*`, and `.agent-docs` appear in its `.git/info/exclude`, preserving existing entries; verify both paths with `git check-ignore` from the main repository. Never change `.gitignore`. Keep records directly in the main repository's `.agent-docs/`, not inside linked worktrees. Inspect `git status`, branch, worktrees, starting revision, and pre-existing edits. Preserve user changes, comments, and docstrings; never stash, reset, or overwrite them for setup. Capture enough pre-task state to restore candidate edits at a retry cap. Run a relevant baseline once when needed, retaining existing failures. Load [workspace preparation](../_workflow/workspace.md) for worktree creation, service/resource isolation, dependency setup, or uncertain workspace details. Ordinary in-place work needs no additional workspace procedure read.
4. **Red and green.** For behavior changes, load [test integrity](../_workflow/testing.md), add a focused regression test, and observe its meaningful failure before implementation. Use autopilot TDD unless human-guided TDD was requested. Record exact commands and verbatim red/green outputs. Implement without weakening assertions; log post-red changes under `Test amendments` for independent reviewer sign-off. No intermediate test/feature commits or temporary-index snapshots. For non-code work use suitable static, rendering, or dry-run checks; purely visual fixes may use reproducible before/after browser evidence. Check affected integration and rerun checks invalidated by the repair. UI verification covers accessibility, interactions, desktop/mobile viewports, and screenshot proof under [verification](../_workflow/verification.md). Retain lengthy output once in the proof or existing logs and link concise summaries without hiding failures.
5. **Review.** Obtain fresh [independent review](../_workflow/review.md) of the patch and integration boundary using [the reviewer brief](../_workflow/templates/reviewer-brief.md). Supply criteria, candidate/base, red/green evidence, amendments, and verdict requirements. Record findings, resolutions, amendment sign-off, and limitations. Cap failed implementation attempts at three and review-fix rounds at three. Every follow-up repair still needs step 2 approval. At an in-place cap, restore only candidate edits to their pre-task state, preserve prior user changes, and record failures. Material scope changes return to planning.
6. **Handoff.** Record cause, change, acceptance proof, review verdict, limitations, and any invalidated parent evidence/task status in the same record. Verify before claiming success. Stage candidate changes with `git add`, leave commits to the user, and never push or deploy. Load [handoff](../_workflow/handoff.md) for detailed staging, changed target state, or isolated-worktree merge instructions. Preserve core's dependency and destructive-action authorization rules throughout.
