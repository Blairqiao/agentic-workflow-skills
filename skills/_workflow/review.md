# Independent review

Inputs: requirements, candidate diff against base revision, recorded red and green verification outputs, and logged test amendments. Exclude the implementer's conversation and internal reasoning from the review brief; include design decisions and `<main-repo>/.agent-docs/CONTEXT.md` definitions needed to understand intended behavior.

1. **Use observable independent review.** Native independent review can satisfy the requirement for boost-track and boosted one-shot when the independent role, reviewed candidate scope, findings, and disposition are observable. A boost success label alone is insufficient. Do not automatically add a second custom review pipeline. If required evidence is absent, obtain a targeted independent review of the missing scope or mark review incomplete. For non-boost execution, use a fresh review subagent packaged with [the reviewer brief template](templates/reviewer-brief.md), including on fast-track, scoped to the patch and its affected integration boundary. Select a high-reasoning model tier when the harness supports model selection. If subagents are unavailable, use an independent session supported by the harness. If neither is available, interactive tracks ask the user before substituting self-review, whereas one-shot performs self-review and records the loss of independence.
2. **Verify requirements and domain terms.** Check each acceptance criterion against the implementation and its automated or manual evidence. Verify that new types, identifiers, and specifications respect `<main-repo>/.agent-docs/CONTEXT.md` when present. Review interfaces and failure handling across the complete candidate diff rather than isolated tasks only.
3. **Audit test integrity.** Compare the test changes in the candidate diff against the acceptance criteria and the recorded red failure and green pass outputs. Check for weakened assertions, missing edge-case coverage, fixture-specific production branches, or inappropriate mocks. Explicitly accept or reject every test amendment listed in the proof. Reproduce test commands directly when evidence is incomplete or a finding needs confirmation.
4. **Check security and data boundaries.** Review security when the change affects input handling, authentication, authorization, stored data, dependencies, or external boundaries. Verify dependency authorization already granted rather than asking again. Check migrations for data loss, locking, and rollback safety.
5. **Report and resolve findings.** Separate blocking defects from optional polish, giving exact file locations and consequences. Resolve technical disputes using requirements and observed evidence. Cap review-fix cycles at 3 rounds. If blocking findings remain after 3 rounds, follow the failure and rollback policy in [core](core.md): restore modified candidate files to their pre-task state for in-place runs, record what was tried and why it failed in `.agent-docs/`, and record a bounded blocker for interactive tracks or report an incomplete outcome in one-shot.

Record the review verdict in the taskboard, compact boost proof, parent proof for a fast-track follow-up, standalone fast-track record, or one-shot run document using [the review template](templates/review.md). No separate review file or numeric score is required. Re-review code changes that address blocking findings without restarting a full audit for minor wording edits.

Check affected project documentation against the resulting behavior and source evidence, ensuring requirements were not rewritten to hide code defects. Keep this check scoped to the change and record unrelated documentation gaps for a separate research audit.

Completion: blocking findings are resolved and verified, every test amendment is explicitly accepted or rejected, or unresolved findings after three rounds trigger the track's rollback and escalation policy. The record states whether review was independent.
