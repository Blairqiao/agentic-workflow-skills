# Explain a project

Inputs: repository, existing documentation, user's learning goal or requested depth.

1. Locate the README, documentation index, architecture and development guides, module documentation, and domain dictionary. Follow their links to identify the project's actual documentation structure. Read the relevant documents; a list of filenames is not an explanation.
2. Determine whether the documents provide a usable project overview and a way to understand its major parts. A license, empty index, or unrelated README alone is not usable project documentation. If no usable documentation exists, disclose the need to bootstrap it and follow [Audit](research-audit.md) to create it before continuing. Explicit read-only instructions prevent creation; provide a source-backed explanation and report the missing documentation instead. If documentation exists but has gaps, explain what is available, identify the gaps, and check relevant code without automatically expanding to a full audit.
3. Organize the explanation around the user's goal. Start with the project's purpose and how its major parts fit together. Follow an important flow through the relevant modules, introduce canonical domain terms, and explain setup and verification when relevant. Link to the existing guides and source files or symbols so the user can follow the explanation themselves.
4. Check source where necessary to support central claims or resolve unclear documentation. Attribute unchecked statements to the document; label inference and separate current implementation from documented intent. Disclose contradictions with source evidence. Do not silently update existing documentation or imply that these targeted checks constitute a complete audit.
5. Walk the user through manageable sections and answer follow-up questions at their requested depth. For a requested single summary or one-shot run, provide a self-contained explanation without feedback gates. Close with a useful reading order, discovered gaps, and any limitations on what was verified.

Completion: the user has a coherent, linked explanation of the project at the requested depth. Missing documentation has been created through Audit when permitted, and unchecked claims, gaps, and contradictions are explicit. A project explanation describes how the system works; a development walkthrough remains the historical record of a particular change.
