# Execution and delegation

Inputs: a named ready plan authorized for execution, or an autonomous one-shot plan, selected executor, workspace, and verification commands.

1. Load the exact plan path recorded at entry. Use one execution slug for the plan, taskboard, proof, images, and workspace references. Concurrent runs need distinct slugs. Builders must not edit settled plan decisions. Reconcile an altered plan before dependent work continues.
2. Keep records at the main repository root. Full and experimental orchestration use [the taskboard](templates/taskboard.md). Boost uses a compact [proof](templates/proof.md) and adds a taskboard only when durable coordination needs it. One-shot uses [the run record](templates/run.md). Fast-track follow-up defects append to the parent proof when available and update affected task status. Standalone fast-track uses [its record](templates/fast-track.md) in a single chat. Update records in place and archive lengthy superseded output.
3. Apply the selected execution policy:
   - Boost owns internal task decomposition, worker dispatch, scheduling, and implementation for boost-track and boosted one-shot. Supply the exact plan, workspace, protected paths, sources, acceptance criteria, evidence locations, and completion format. Do not add a mandatory custom taskboard, worker-per-task policy, model allocation, or duplicate review pipeline around native boost.
   - Full-track uses non-boost execution and mandates scoped implementation subagents. The coordinator manages dependencies and reviews evidence. Use [implementer briefs](templates/implementer-brief.md) and the active adapter's supported capability tiers.
   - Experimental orchestration uses non-boost custom coordination and verifiable vertical slices. Delegate implementation to supported standard coding agents and escalate demanding fixes after round two to a high-reasoning agent. Do not silently nest orchestration around boost.
   - Fast-track implements directly without boost or implementation subagents in the existing candidate checkout. Repair only mismatches with approved behavior. Describe the defect, expected behavior, likely files, and checks, then proceed under the parent authorization. Standalone fixes execute after inline mini-spec approval. A new feature remains new scope even when small.
   - One-shot is explicit-only and plans and implements autonomously with either boost or non-boost execution. Record the executor and do not silently switch. Non-boost one-shot delegates independent tasks when coordination helps; boosted one-shot leaves internal delegation to boost.
4. Give custom simultaneous writers disjoint file scopes and isolated resources. Follow [workspace preparation](workspace.md) for persistent candidates and native worker boundaries. Use [discovery](discovery.md#code-exploration-and-delegation) for read-only investigation. Do not create user-visible sidebar chats as an implementation mechanism unless requested. Antigravity custom coordinators use reactive wakeups rather than polling.
5. Follow [test integrity](testing.md). Inspect observed red and green command evidence and test amendments. Never invent missing red output after implementation. Reproduce checks when evidence is missing, suspect, or invalidated by integration. Use [independent review](review.md) and record its scope and findings before marking requirements complete.
6. Material changes to behavior, scope, dependencies, risk, or external effects return to the planning phase. Record the blocked decision and continue independent authorized work. Changed scope needs a revised ready plan and a new execution instruction. One-shot resolves choices autonomously within its authority and records its rationale; safety and dependency permissions still apply.

Cap failed task implementation attempts at 3 and review-fix cycles at 3 rounds. Track corrections across executor boundaries rather than resetting counts. If a cap is reached during an in-place run, restore only modified candidate files to their pre-task state while preserving user changes and the failure record. Follow [core](core.md) for escalation. Native internal attempt counts may be unavailable; report that limit rather than claiming they were enforced or resetting observable custom attempts.

Completion: scoped tasks are implemented, reviewed, and evidenced, or remaining blockers and required rollback are accurately recorded.
