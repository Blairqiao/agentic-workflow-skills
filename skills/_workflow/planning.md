# Implementation planning

Inputs: planning specification, discovered commands, repository constraints, and selected executor. The execution phase adopts this plan and validates its current state rather than repeating planning.

1. Divide full and orchestration work into coherent tasks with goals, acceptance criteria, expected files, dependencies, risks, and verification. Orchestration uses vertical slices. For boost, specify deliverables and boundaries while leaving internal decomposition and dispatch to native boost. A standalone fast-track repair executes in a single chat using a lean mini-spec. A follow-up defect within approved behavior reuses the parent plan and proof, while every follow-up repair in interactive tracks requires new mini-spec approval under core before code or test edits. One-shot records an autonomous plan in its run document.
2. Choose checks that prove observable behavior. Use meaningful failing tests for behavioral changes, characterization for legacy behavior, and browser, dry-run, or document checks where appropriate. Include relevant project documentation in scope when behavior, setup, interfaces, or architecture changes.
3. Use autopilot testing unless the user requests [human-guided TDD](../human-tdd/SKILL.md). Record the choice once. One-shot always uses autopilot.
4. Record scope, exclusions, acceptance criteria, expected files, verification commands, target checkout and branch, starting revision, protected user edits, permissions, selected executor, and unresolved blockers. List new dependencies, migrations, external effects, and authorization needed. Plans with unresolved consequential blockers cannot be ready.
5. Write the combined specification and plan using [the plan template](templates/plan.md) in `<main-repo>/.agent-docs/plans/<feature>.md`. Follow [core execution identity rules](core.md#operation-routing-and-records) for concurrent runs. Standalone fast-track repairs record their mini-spec and execution evidence in `<main-repo>/.agent-docs/fast-track/<feature>.md`. One-shot keeps its plan in `<main-repo>/.agent-docs/runs/<feature>.md` and proceeds without interactive gates.
6. Mark the completed plan `ready`, present scope, affected files, strategy, and acceptance criteria inline in chat, and provide a copyable execution instruction with exact plan path and executor. Plan readiness alone grants no implementation permission. The user's explicit instruction to execute the named ready plan grants authorization within scope. Do not repeat the initial named plan approval during execution; preserve the separate approval gate for every follow-up repair. Always place a direct clickable link to the authoritative plan artifact at the very bottom of the chat response.

On adoption, execution checks the plan against the actual checkout, branch, starting revision, and protected edits. Reconcile drift before dependent work. A missing prerequisite leaves affected work blocked. Material changes to behavior, scope, dependencies, external effects, or risk return to the planning phase. Update the authoritative plan, resolve consequential blockers, and obtain a new explicit execution instruction for changed scope. Continue independent authorized work while a decision is blocked.

On retry, update the same execution record rather than allocating another identity. Expected files are planning aids; ordinary supporting edits within the initial task need no new gate. A follow-up repair remains subject to its mini-spec approval gate. Preserve prior evidence and a brief history, archiving lengthy superseded detail in `.agent-docs/archive/`.

Completion: The planning phase has delivered a complete ready plan and execution instruction with the plan link at the bottom of the response, or has saved a paused record with blockers. The execution phase has validated the exact plan and execution authorization before implementation.
