# Agent guidelines for the agentic workflow

> These rules govern planning, test-driven execution, independent review, verification, and handoff across projects using the agentic workflow.

## Core behaviors

1. **Evidence over assertions.** Never claim a bug is fixed or a feature works without running the relevant test or verification command and observing the output. Record the terminal proof.
2. **Design first and track selection.** Do not write implementation code without a plan. Read `<main-repo>/.agent-docs/CONTEXT.md` when present. Use [brainstorm](skills/brainstorm/SKILL.md) for exploratory problem framing, [grilling](skills/grilling/SKILL.md) for scoped decision stress-testing, and [domain-modeling](skills/domain-modeling/SKILL.md) for domain terminology. Exploration alone does not start a track or authorize implementation. When implementation planning or implementation is requested, select the track automatically between `full-track` and `fast-track` if the user does not specify one, while reserving `one-shot` for explicit user requests:
   - **Full-track.** Use [full-track](skills/full-track/SKILL.md) for multi-step features, architectural changes, new dependencies, or tasks that benefit from worktree isolation and mandated subagent delegation. Full-track mandates subagents for all task implementation. Maintain three documents in `<main-repo>/.agent-docs/` using a short, stable `<feature>` slug: the combined spec and plan in `plans/<feature>.md`, the taskboard in `taskboard/<feature>.md`, and the combined proof and walkthrough in `proofs/<feature>.md`.
   - **Fast-track.** Use [fast-track](skills/fast-track/SKILL.md) for linear, single-session changes in the current workspace that do not require multi-step task decomposition or implementation subagents. Record the mini-spec, acceptance criteria, red and green test evidence, review verdict, and proof in `<main-repo>/.agent-docs/fast-track/<feature>.md`, and escalate to `full-track` if scope outgrows a single linear task.
   - **Approval gates and inline presentation.** Every approval gate, whether initial or follow-up defect or pivot, must display the plan or mini-spec inline in chat covering scope, affected files, technical strategy, and acceptance criteria, and pause for explicit approval before editing code or tests.
   - **One-shot.** Use [one-shot](skills/one-shot/SKILL.md) only when explicitly invoked by the user. Start immediately without feedback gates and record autonomous decisions, plan, progress, review, proof, and walkthrough in `<main-repo>/.agent-docs/runs/<feature>.md`.
   - **Retry caps and rollback.** Cap failed task implementation attempts at 3 and review-fix cycles at 3 rounds across all tracks. If a cap is reached during an in-place run, restore modified candidate files to their pre-task state while recording what was tried and what failed in `.agent-docs/`.
3. **No phantom edits.** Preserve existing comments, docstrings, and unrelated logic when making edits. Modify only what belongs to the approved scope.
4. **Evidence-based red and green testing.** Default to autopilot TDD for behavior changes unless the user requests [human-tdd](skills/human-tdd/SKILL.md). One-shot always runs autopilot TDD. Follow [test integrity](skills/_workflow/testing.md): write or update the test first, run it and record the verbatim red failure output before writing implementation code, implement green without weakening assertions, record the verbatim green pass output, and log any post-red test revisions under `Test amendments` for explicit reviewer sign-off. Do not create `test(red)` or `feat(green)` Git commits or temporary-index tree snapshots.
5. **Clean handoff and Git safety.** Follow [integration and handoff](skills/_workflow/handoff.md). Never run `git commit` on the target branch, deploy, or run `git push`. For in-place runs, enforce a no-commits rule during execution and stage candidate changes with `git add` at handoff. For isolated worktree runs, keep work inside `<main-repo>/.worktrees/<feature>`. At handoff, provide the worktree path, branch name, and complete merge instructions for `<main-repo>`: (1) change directory back to `<main-repo>`, (2) run `git merge --squash <worktree-branch>`, (3) run `npx tsc --noEmit && npm test` to verify integration against target branch changes, (4) commit the staged squashed changes with a suggested commit message, and (5) optional worktree cleanup commands.

## Execution and verification standards

1. **Workflow tool skills.** Invoke specialized tool skills according to task needs:
   - **Brainstorm.** Use [brainstorm](skills/brainstorm/SKILL.md) to explore ideas and save every completed or paused brief. Before a track starts, use `<main-repo>/.agent-docs/briefs/<feature>.md`; during a track, update its existing artifact. On handoff, incorporate the decisions and mark the brief handed off with a link to the authoritative track document. Respect explicit chat-only requests and preserve each track's approval policy. One-shot applies shared design rules autonomously without interactive brainstorming or grilling.
   - **Domain modeling.** Use [domain-modeling](skills/domain-modeling/SKILL.md) to build and maintain the shared domain dictionary in `<main-repo>/.agent-docs/CONTEXT.md`.
   - **Grilling.** Use [grilling](skills/grilling/SKILL.md) to stress-test requirements, architectural decisions, and tradeoffs in structured rounds before implementation.
   - **Human TDD.** Use [human-tdd](skills/human-tdd/SKILL.md) to align collaboratively with the user on `[Specific]`, `[Intermediate]`, and `[Global]` tests before coding.
   - **Unslop.** Apply [unslop](skills/unslop/SKILL.md) across all authored prose in user-facing documentation, code comments, and internal `.agent-docs/` records while preserving code blocks, commands, and verbatim output.
   - **Research.** Use [research](skills/research/SKILL.md) to explain codebase architecture or audit maintained code against project documentation.
2. **Worktree placement, parent-repo `.agent-docs/`, and `.git/info/exclude` setup.** Follow [workspace preparation](skills/_workflow/workspace.md) before creating a worktree or writing any file in `.agent-docs/`. Add `.worktrees` and `.agent-docs` ignore patterns exclusively to `<main-repo>/.git/info/exclude` without modifying `<main-repo>/.gitignore`. Keep all `.agent-docs/` files in `<main-repo>/.agent-docs/` directly by path, edit active feature records in place, move lengthy superseded history to `.agent-docs/archive/`, and read archived files only when directly relevant. In all authored repository documentation (`.agent-docs/**/*.md`, `docs/**/*.md`, `AGENTS.md`), never use host-absolute paths—neither raw filesystem paths starting with `/Users/` or `/home/` nor `file:///` URLs. Every internal file link and image embed must use repository-rooted paths starting with `/` (e.g. `/.agent-docs/spec/<feature>.md`, `![Caption](/.agent-docs/proofs/<image>.png)`, `/src/components/...`). Reserve clickable `file:///` URLs strictly for chat output.
3. **Universal subagent capability tiers.** When dispatching subagents in multi-agent runners, select models by capability tier:
   - **Lightweight scanning tier.** Use for bounded code retrieval, directory scans, file discovery, and symbol searches.
   - **Standard coding tier.** Use for scoped behavioral investigations and task implementation in `full-track` and `one-shot`. Full-track mandates subagents for task implementation. Read-only investigations are permitted in `fast-track`; implementation subagents are not.
   - **High-reasoning tier.** Use for demanding investigations, architecture tradeoffs, independent review packaged with [the reviewer brief](skills/_workflow/templates/reviewer-brief.md) across all tracks including `fast-track`, and fix escalations after round two.
   Follow [code exploration and delegation](skills/_workflow/discovery.md#code-exploration-and-delegation): delegate broad code reading by default, allow direct documentation and purposeful small code reads, and verify exploration findings only for critical decisions. The orchestrator selects supported models and reasoning settings through the active harness adapter. Read-only exploration does not trigger fast-track escalation.
4. **Multimodal UI verification.** For web or UI changes, do not rely on compiler or build passes alone. Use available browser inspection tools to check accessibility trees, interactive elements, desktop viewports, and mobile viewports such as 390x844, capturing screenshots as evidence. Embed all referenced screenshot proofs in Markdown documentation using image syntax with repository-rooted paths, `![<Descriptive Caption>](/.agent-docs/proofs/<filename>.png)`, rather than host-absolute paths, raw file paths, or plain text links.

## Transparency and honesty

1. **Admit knowledge gaps.** When documentation or context is missing, state what is unknown rather than guessing or inventing APIs.
2. **Disclose shortcuts and debt.** Flag any implementation shortcut, technical debt, or performance risk in the walkthrough.
3. **No silent assumptions.** When a requirement is ambiguous, stop and ask the user, except in `one-shot` where you record the decision and rationale in `.agent-docs/runs/<feature>.md`.
4. **Constructive pushback.** When a proposed approach is flawed, insecure, or conflicts with project architecture, explain the issue before implementing it.

## Guardrails and safety

1. **No placeholders.** Write complete implementations. Never leave `// TODO`, `/* implement here */`, or truncated snippets unless prototyping was explicitly requested.
2. **Dependency discipline.** Do not install new third-party dependencies without prior user confirmation and justification.
3. **Destructive action safety.** Never run destructive Git commands such as `git reset --hard` or `git push --force`, drop databases, or delete user directories without explicit confirmation.
